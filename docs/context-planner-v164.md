# 문맥 기반 행동 계획기 (v164)

## 이전 구조와 변경 범위

운영 `/api/chat`은 AI 분석 이전에 `phase1ChatResponse`로 반환했다. 위치·거리·음식·예산·시간·대상 식당은 `phase1-core.js`의 정규식과 고정 단계가 결정했고, 서비스/인사/초기화도 먼저 규칙으로 반환했다. 기존 AI 분석 함수가 있어도 이 운영 경로에서는 실행되지 않았다.

이제 운영 진입점은 `contextualChatResponse` → Responses API의 strict JSON Schema 행동 계획 → 서버 검증 → 기존 검색/증거 확인 도구다. 행동은 일반 대화, 확인 질문, 새 검색, 다른 식당 검색, 조건 변경 검색, 상세 조회, 비교, 지도, 고정 FAQ, 초기화다. 장소 이름·메뉴 표현의 키워드 일치가 운영 의도를 선점하지 않는다. 검색 후보 일치, 데이터 형식, URL 허용 목록, 실제 거리, 가격/영업 근거 검사는 계속 코드가 담당한다.

이전 무조건 반환 뒤의 도달 불가능한 약 430줄 연결/모드 파이프라인을 제거했다. 예전 파서와 서비스 분기는 기존 비교용 fixture를 재실행하는 서버 환경값 `CONVERSATION_PLANNER_MODE=legacy-test`에서만 접근한다. 클라이언트가 이 모드를 요청할 수 없다. 운영 실패 시 이 파서로 폴백하지 않는다. 기존 평가 예시·학습 후보 데이터·1,099곳 실제 자료는 삭제하지 않았다. 사용되지 않는 구형 분석 보조 함수의 추가 정리는 실제 모델 운영 검증 후 별도 진행한다.

## 문맥과 상태

- 브라우저 전송 기록: 최근 24개 역할/본문만, 각 2,400자. 카드의 대용량 메뉴/추천 묶음은 전송 상태에서 제외하고 서버 원본으로 복원한다.
- AI 입력: 최근 12개 메시지(각 1,800자), 현재 확정 조건, `explicit/default/inherited/unset` 출처, 대기/이전 질문, 미확인 표시 동의, 현재 카드 3개와 과거 카드 최대 12개, 사용자의 현지 시간, 선택 위치 식별자.
- 세션 ID가 다르면 조건·식당 대상·기기 좌표를 승계하지 않는다. 새 대화의 첫 요청에는 과거의 미결합 상태도 승계하지 않는다. 같은 대화의 핵심 조건은 최근 메시지 범위 밖이어도 유지한다.
- AI는 조건 전체를 재작성하지 않고 `changes[{slot,op,value}]`만 낸다. 서버가 숫자 범위·유형·중복 변경·실제 식당 ID·허용 FAQ ID를 검사한다. 분석 메모는 반환 payload에 넣지 않는다.
- 위치 변경은 기존 좌표를 먼저 제거한다. 등록 기준점이면 테이블에서, 그 외 정확한 역은 기존 공식 지역 검색으로 이름/유형이 일치하고 좌표가 하나로 확인될 때만 정한다. 광화문은 광화문역 조회를 사용한다. 조회 실패/모호함은 질문하며 과거 좌표를 재사용하지 않는다.
- 위치/반경이 확정되면 실제 검색을 실행한다. 음식·가격·인원·시간은 필수 질문 단계가 아니다. 결과 조건 표시는 계속 일반 텍스트다.
- 일반 식당 사실은 모델이 작성하지 않고 기존 원본/검색 도구가 출력한다. FAQ는 모델이 선택한 ID의 고정 답변이다. 대화와 카드 텍스트는 지침이 아닌 비신뢰 자료로 전달한다.

## 실패 처리와 운영 조건

기존 서버 `OPENAI_API_KEY`와 기존 모델 설정을 사용한다. 키를 조회/생성/출력/저장하지 않았다. 모델은 `OPENAI_INTENT_MODEL` → `OPENAI_MODEL` → 기존 기본 `gpt-5-mini` 순서다. Responses 구조화 출력 호출 제한은 10초, 출력 상한은 1,800토큰이며 `store:false`다. 명시적 중지 설정은 `CONVERSATION_PLANNER_DISABLED=true`다. 옛 `INTENT_ANALYZER_DISABLED`는 새 흐름에 적용되지 않는다.

키/모델 사용 불가, 시간 초과, 잘린 JSON, 계약 위반이면 검색을 실행하지 않고 조건을 보존하며 재시도를 제공한다. 낮은 자신감이면 변경 없이 확인 질문이다. 기존 로딩/오류/재시도 UI와 45초 클라이언트 제한은 유지한다. 새 정책 버전 `v164`로 이전 응답 캐시를 무효화한다.

## 지도 링크

v161의 `naver-map.js`와 원본 주소·상호에 결합된 `naverPlaceVerification`을 유지한다. 실제 1,099개 원본 URL/ID의 연결 근거(엑셀 수집/매칭 기록)를 사용하며, 이번 작업에서 전체 링크 목적지를 새로 실사한 것은 아니다. 허용된 네이버지도/플레이스 URL의 검증된 상세 링크면 **지도 보기**, 없으면 상호·지점·주소 검색과 **네이버지도에서 검색**이다. API `link`나 임의 ID를 상세 링크로 채택하지 않는다. 수동 등록은 기존 `scripts/register-place-link.mjs`를 사용한다. 자료 수집일은 영업 정보의 현재성이나 추천 작성일을 보증하지 않는다.

## 검증 결과와 한계

`node scripts/build-worker.mjs`와 `node scripts/policy-smoke.mjs` 통과. 새 `context-planner-smoke.mjs`는 운영 Worker의 기본 경로를 호출하되 모델/네이버 응답만 가로채며 가짜 인증 문자열만 사용한다. 테스트 출력은 배포 데이터에 포함되지 않는다.

검증: 광화문 점심 → 반경 질문 → 1km 검색 → 더 저렴한 곳 예산 확인(조건 유지) → 홍대 위치만 변경(좌표 교체) → 반경 설명(조건 유지) → 모호한 해제 확인 → 새 대화 격리. 추가로 잘못된 행동/음수 반경/가짜 식당 ID/중복 변경 거부, 모델 오류·시간 초과·JSON 실패 시 무검색, 최근 기록 제한, 실제 원본 식당·메뉴·추천인 연결, 상세 링크 복원, 미확인 항목 동의, 거리 필터, 기존 클라이언트의 질문/카드 렌더를 검사한다.

**모킹의 한계:** 이 결과는 모델의 실제 의도 해석 정확도나 실제 광화문 좌표 검색 성공을 측정하지 않는다. 실제 AI 평가·키 확인은 사용자 지시에 따라 하지 않았다. 현재 모델/키 설정의 운영 사용 가능 여부, 모든 지점 링크 실사, 실제 휴대폰의 지도 앱/웹 전환과 기기 위치는 미검증이다. 데스크톱/모바일의 기존 DOM/CSS·지도 도메인/동명·지점 구분 회귀는 자동 검사했으며 이번 버전의 실기기 렌더 시연을 대신하지 않는다.
