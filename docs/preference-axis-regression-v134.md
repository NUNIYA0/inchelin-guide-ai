# v134: 조건 후보 유지·이어서 질문 축 복원

## 원인과 수정

1. 첫 네이버 결과는 도로명주소와 지번주소를 함께 검증하지만, v133의 카드/상태에는 지번주소가 없었다. 도로명에 지역 별칭이 없고 지번의 서교동·성수동·여의도동 등으로 지역을 확인한 식당은 다음 조건 턴에 재검증할 때 탈락할 수 있었다. 강남구가 도로명에 남는 강남 검색과 차이가 나는 경로다. 사용자 브라우저의 당시 원본 결과를 조회한 것은 아니며, 실제 주소 형태의 모킹으로 이 손실 경로를 확인했다.
2. 카드의 지번주소(parcelAddress), 원분류, 확인된 메뉴 정보를 상태와 브라우저 왕복에 보존하고 restoreCardPlace 공통 함수로 검색 데이터 구조를 복원한다. 카드 표시에 주소 줄을 추가하지는 않는다. 같은 음식·지역의 선택은 기존 ID를 우선 유지하며, 확인된 시설 근거로만 순서를 바꾼다. 3곳이면 주 검색을 생략하고, 부족할 때만 새 검색 결과를 합쳐 3곳까지 보충한다. 근거 없는 조건은 안내만 붙인다.
3. 동행 답변은 다른 검색 라벨/새 주제 표시로 분석되더라도 기존 축을 초기화하지 않게 통일했다. 구체 메뉴가 같으면 상위 음식 분류의 중복 표기 차이로 유지 경로에서 빠지지 않는다. 음식·지역 변경, 다른 곳 요청은 기존 별도 경로를 유지한다.
4. 이어서 질문의 존재 확인도 렌더링 카드 자체를 검색 결과로 오인해 검증하고 있었다. 이 경로에도 restoreCardPlace를 적용해 현재 결과로 확인 가능한 조합은 재검색 없이 확인한다.
5. v133의 같은 축 상세 질문으로 개수를 채우는 폴백은 제거했다. 장소 응답은 축 중복 금지, 상세 최대 1, 비교 최대 1(실제 식당 2곳 이상)이다. 대기 질문이 있으면 상세/비교 1 + 지역/음식 1로 2개, 없으면 서로 다른 축 3개이며 지역/음식/상황을 적어도 1개 포함한다. 식당명 원문·지시어 금지·세션 중복·문형 반복 방지·서버 분류/존재 검증은 유지한다.
6. 첫 지역/음식 대안이 실패해도 즉시 상세 축으로 대체하지 않고 지원 지역·메인 메뉴의 다음 조합으로 진행한다. 최대 6개씩 3회 병렬 검증(최대 18개, 각 회 최대 850ms)하며 충분해지면 중단한다. 기존 짧은 결과 캐시를 재사용하며 추가 AI 호출은 없다. 파스타·초밥에 메인 메뉴 대안도 보강했다.
7. 상세/비교 식당명 속 음식명이 지역 '~면' 등으로 잘못 추출되어 검증에서 탈락하는 경우를 모킹 중 확인했다. 이미 알려진 식당명은 축 추출에서 제외하고 식당 참조로 처리한다.
8. RESPONSE_RULES_VERSION을 v134로 올려 v133 응답이 현재 규칙으로 재사용되지 않게 했다.

## 테스트 결과

- node scripts/build-worker.mjs: 통과, 35개 자산 포함.
- node scripts/policy-smoke.mjs: 전체 통과. 외부 네트워크는 모킹하며 실제 AI/Naver 평가는 실행하지 않았다.
- 홍대 냉면 / 성수 파스타 / 역삼 국밥 / 여의도 초밥 × 혼자 / 2~3명 / 회식 / 가족 = 16건 모두 기존 ID 3곳 유지(3→3).
- 위 4개 조합별 부족 후보 보충 4건, 분석 라벨·새 주제 분기 보정 4건 통과.
- 실제 프런트 normalizeMessage → buildAIRequest → 서버 왕복에서 지번주소 보존 확인.
- 대기 중 2개(상세/비교+지역/음식), 비대기 3개, 서로 다른 축, 상세/비교 상한, 뒤쪽 지원 조합 폴백 통과.
- 기존 첫 화면 5개 추천 행 통합 테스트도 새 2개 구성 규칙으로 통과.
- 검증 거절/시간초과/모든 안전한 풀 소진 시에는 존재를 지어내거나 같은 상세 축을 중복해 개수만 맞추지 않는다. 따라서 모든 검증이 실패하는 예외에서는 2/3개를 보장할 수 없으며, 모킹은 이 안전 동작도 확인한다.
- 키 파일 확인, 실제 AI 평가, 라이브 대화·브라우저 픽셀 확인은 하지 않았다.
