# v132 연관 질문 순환 · 첫 요청 지연 · 새 대화 분리

## 1. 적용한 내용

- 장소 응답의 축 풀은 지역/메인 음식/상황/실제 식당 상세/비교입니다. `relatedAxisHistory`에 직전 두 응답을 저장하고 최근에 덜 쓴 축을 우선합니다. 5개 축에서 매 응답 3개를 고르면 직전 두 응답과 완전 무중복은 수학적으로 불가능하므로, **최근 미사용 축 우선 → 불가피한 중복 최소화**로 구현했습니다.
- 모킹 회귀에서 `지역·음식·상황 → 상세·비교·지역 → 음식·상황·상세` 순환을 확인했습니다. 대기 질문이 있으면 최대 2개, 없으면 3개를 목표로 하며 분류/결과 존재 검증 실패 시 억지로 채우지 않습니다.
- 현재 회식/혼밥 상황을 잇는 다른 식당 찾기도 상황 축으로 취급합니다. ‘회식하기 좋은 다른 삼겹살집도 보여줘’는 음식·지역을 유지하고 기존 노출 식당을 제외합니다. 아직 답변 대기 중이거나 ‘상관없어요’로 건너뛴 동행 질문은 다시 제안하지 않습니다.
- 연관 질문에 첫 번째/두 번째/마지막/거기 같은 모호한 지시어를 허용하지 않습니다. 상세·비교는 실제 가게명을 그대로 쓰고 **이 두 축만 최대 40자**를 허용합니다. 이름을 줄이지 않으며 40자를 초과하면 해당 제안을 제외합니다. 사용자가 직접 입력하는 서수 질문의 기존 해석 기능은 유지합니다.
- 시작하기(PC/모바일)·새 채팅·가입 완료 후 시작은 빈 대화로 초기화합니다. 지난 대화는 사이드바의 명시적 선택으로만 엽니다. 이력은 활성 메시지 배열의 별칭이 아닌 JSON 스냅샷으로 보관합니다.
- 대화 세대 번호와 요청별 타이머 소유권을 추가했습니다. 취소된 이전 요청의 응답/오류/위치 결과는 새 대화에 반영되지 않으며, 이전 요청의 finally가 새 요청의 타이머를 지우지 못합니다. 새 대화 ID도 충돌을 피하도록 고유 ID로 생성합니다.

## 2. 운영 로그 확인 — 사실과 한계

읽기 전용 Sites Worker 로그에서 최근 180분의 이벤트 최대 100개를 확인했습니다. 새 테스트 요청을 보내지 않았습니다. 확인된 `/api/chat` 두 건은 다음과 같습니다(한국 시간).

| 시각 | 상태 | Worker wall time | CPU time |
|---|---|---:|---:|
| 2026-10-21 17:41:34.510 | 200 | 9,658ms | 227ms |
| 2026-10-21 17:41:55.300 | 200 | 4,938ms | 206ms |

이 두 요청이 사용자 세션의 첫/두 번째 요청인지는 확인할 수 없습니다. 제보된 약 40초 요청은 조회 범위에서 특정하지 못했습니다. 기존 로그에는 단계별 타이밍이 없으므로 초기 구동·모델·네이버 중 하나를 40초의 확정 원인으로 단정하지 않습니다.

코드에서 확인한 누적 대기 경로와 변경은 다음과 같습니다.

| 경로 | 이전 | 이번 변경 |
|---|---|---|
| 연관 질문 사전 검색 | 최대 6개를 직렬 대기 | 최대 6개 병렬, 축당 2개 조합, 개별 상한 850ms |
| 결과 존재 캐시 | 완료 결과만 재사용 | 진행 중 동일 조합도 합류, 기존 양성 180초/음성 15초 캐시 유지 |
| 네이버 대체 검색어 | 최대 3개 순차, 호출당 6.5초 | 같은 음식·지역 검증을 유지하며 병렬, 첫 유효 결과 즉시 사용(느린 대체 검색을 기다리지 않음), 일반 호출 3초/사전 검증 650ms |
| 의도 분석 JSON 본문 | 응답 헤더 이후 본문 대기 상한이 분리되지 않음 | fetch부터 JSON 파싱까지 동일 2초 제한, 기존 최대 1회 재시도 유지 |
| 답변 생성 | 각 헤더 대기 6.5초 | 첫 생성 5.5초, 말투 재생성 2.5초, JSON 본문 각 2초 |
| 15초 이상 클라이언트 대기 | 동일 로딩만 유지 | ‘먹을 곳을 찾는 중이에요. 조금만 기다려 주세요.’ 표시 |

일반적인 음식+지역 검색은 검색어가 1개이므로 네이버 대체 검색어 병렬화가 항상 작동하는 것은 아닙니다. 명시적인 음식 조건은 계속 유지하며 관련 없는 식당으로 채우지 않습니다. 링크 조사 경로 전체를 이번 속도 수치로 일반화하지 않습니다.

배포 후 `Server-Timing` 응답 헤더와 `chat_timing` 숫자 로그에 intent/search/details/copy/decode/policy/suggestions/total을 기록합니다. `firstInIsolate`는 해당 Worker 인스턴스 첫 요청 표시일 뿐 초기 구동 시간의 측정값은 아닙니다. 로그에는 사용자 문장·검색어·키·요청 헤더를 추가하지 않습니다.

## 3. 단계별 계측 — 모킹이며 실제 AI 속도가 아님

네이버 응답마다 30ms, 답변 생성에 60ms 지연을 주입한 목 데이터의 대표 1회 계측입니다. 첫 검색은 빈 애플리케이션 세션, 다음 검색은 ‘회식이에요’ 답변입니다. 실제 모델/API 성능이나 40초 문제 해소의 실측값이 아닙니다.

| 단계 | 첫 검색 | 다음 검색 |
|---|---:|---:|
| 의도 정책 | 1.4ms | 0.6ms |
| 식당 검색 | 32.2ms | 40.5ms |
| 상세 정보 | 0ms | 0ms |
| 답변 생성 목 응답 | 63.1ms | 66.5ms |
| JSON 해석 | 0.1ms | 0ms |
| 응답 정책 | 0.1ms | 0.1ms |
| 연관 질문 분류·사전 검증 | 133.0ms | 135.2ms |
| 전체 | 236.4ms | 250.1ms |

별도 합성 지연 35ms × 6개 사전 검증 벤치마크는 직렬 264ms / 병렬 49ms였습니다. 환경 스케줄링과 분류 CPU 때문에 주입 지연보다 실제 계측값이 더 클 수 있습니다. 이는 병렬화 회귀 확인이며 운영 응답속도 개선율로 해석하지 않습니다.
